Agent-readable code: what the rules actually change

engage output-style study · 5 tasks · 14 rule-sets · 109 generation runs + 27 neutral-reader modifications · evaluated by Fable 5.1 · 2026-09-03 · applied to all four styles the same day

TL;DR
  1. Correctness is a ceiling. Every rule-set — including "no rules" — passed 100% of the hidden edge-case suites on all five tasks (109 runs), every output was correctly extended by a neutral reader agent (27/27), and 60 modules pass tsc --strict --noUnused* with 0 errors. On single-module tasks, rule text does not move correctness. Don't claim "bug-free."
  2. Rules change structure and cost, a lot: a 2.6× token spread, comment density 0→25 lines, whether the domain is encoded in types, whether clever idioms appear.
  3. Compressing the wording is free. Engage rewritten 19% shorter produced the same code fingerprint. Same for the fuller bundle at −20%.
  4. The middle ground is "M-min": the same rule-text size as today's engage (445 vs 443 tok), contracts on every export, zero clever idioms, +44% generated-code tokens — versus +113–119% for the fuller bundles, whose extra cost comes from line-multiplying rules (one-idea-per-line, explicit loops, edge enumeration), not from readability essentials.

Reading the outputs (t4 CSV, t5 SemVer)

  • base: monolithic, nesting 4–6, restates the spec in a 15–37-line JSDoc plus inline "what" comments — the redundant-doc pattern research says rots.
  • engage: lean, decomposed, flat. But: positional tuple returns, a dense one-liner dispatch from rule 5, ordering-by-truthiness (a || b on -1/0/1, find()??0), under-named regexes. "Boring over clever" caught none of them.
  • bundle: domain in types + assertNever, names like INTEGER_WITHOUT_LEADING_ZEROS, contracts, one idea per line. Most readable — and 2.2× tokens, over-built past the spec (bigint, iterator comparer, unrequested validation).
  • no-functional: cheapest, zero clever idioms, same correctness — the pipeline rule is what invites reduce/find-as-control-flow.

What the research says helps agents

  • Dead code is the #1 comprehension killer (LLMs fail to localize a bug in 81% of programs under semantics-preserving mutations).
  • Correct inline comments help little; stale/misleading ones hurt a lot (−23%).
  • Contract docstrings on public symbols are the spec the next agent generates from.
  • Identifier names matter at least as much as comments.
  • Code early in a file is understood better (lost-in-the-middle); small units.
  • LLMs are weak at dynamic semantics: hidden mutation, truthiness tricks, positional tuples.
  • Duplicate structure freely; never duplicate a business rule (agents update one copy).

4 · Recommendation: adopt M-min

What it adds (cost ≈ 0 in rule text, removes things in code)

  • Bans with teeth: no truthiness tricks on numbers/orderings; named object, not positional tuple.
  • Never duplicate a business rule or constant — single-source at first reuse (measured: inline business literals 3→1).
  • No dead code: unreachable branches, unused params/vars, commented-out code.
  • A stale comment is worse than none.
  • Explicit over magic; only call APIs visible in types/repo/docs; no any.

The one add that costs lines — and earns them

  • Contracts on exports: every exported function/type gets a 1–3 line contract (intent, inputs, invariants, what it throws); never a spec restatement. This is the +7 comment lines and most of the +44%. Research: the docstring is what the next agent generates and modifies from.

What it deliberately leaves out

  • One-idea-per-line, mandated explicit loops, edge-case enumeration, parse-don't-validate, branded types, big test files — each a line multiplier (+113–119% together) with no correctness gain here.
  • Any "bug-free" claim.

M-min — proposed engineering block (445 tok, replaces today's 443)

Best code = none. Ladder, first that holds: (1) needed? speculative → skip, say so; (2) stdlib; (3) native platform; (4) installed dep — never add one for a few lines; (5) one line if clearer, not if denser; (6) else the minimum that works. Write for the reader: least complexity, not fewest chars; clearest then shortest. Name for intent; constants for magic literals; named intermediate over dense expression; no ceremony or re-declarations. Duplicate structure freely; never duplicate a business rule or constant — single-source at first reuse. Delete > add. Boring > clever: no truthiness tricks on numbers/orderings (`a || b` on -1/0/1, `?? 0` as control flow); named object, not positional tuple, for multi-value returns. Fewest files; shortest readable diff; entry point first, helpers after. No shallow/speculative abstraction; absorb real recurring complexity behind one deep interface. Explicit over magic: no metaprogramming, decorators, registries, config-driven dispatch. Happy path flat and left: guard-clause edges, return early, no nesting. Prefer map/filter for simple transforms; a plain loop where a reduce would need a comment. No `any`. No dead code: unreachable branches, unused params/vars, commented-out code. Only call APIs visible in types/repo/docs. Perf: simplest correct first; measure before optimizing; climb only on profiler evidence. Comments in bodies: terse, why not what; none that restate code; no banners, no war stories. Every exported function/type: a 1–3 line contract — intent, inputs, invariants, what it throws; never a spec restatement. A stale comment is worse than none. Never drop: input validation at boundaries, error handling against data loss, security, a11y, anything asked. Non-trivial logic leaves one runnable check.

Footprint: style body ≈ unchanged (+2 tok on the engineering block; the rest of the style can take the same 19% wording compression for a net reduction). Generated code ≈ +44% per module vs today — almost entirely the contract comments on exported symbols.

6 · Limitations

  • Ceiling effect: the generating model produced zero bugs on any task, so rule-sets cannot be ranked by correctness here; the honest claim is "no measurable difference at this scale."
  • Scale: single-module tasks. The research-backed harms (dead code, stale comments, drift, magic, position effects) act on real codebases over long sessions — the follow-up is a multi-file repo task with a multi-step change and a weaker reader model.
  • n: 1 sample per cell in round 1, 2 on hard tasks and in round 3; structural means are directional. The qualitative reading is one model's (Fable 5.1) opinion on ~5 files; structural metrics are regex proxies.
